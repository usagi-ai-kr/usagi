# 독자 중심 작성 계약

이 문서는 에이전트 전용입니다. 사람이 읽는 본문의 제목을 프레임워크 약자로 채우지 않습니다.

## 구성

- 먼저 독자, 목적, 한 문서의 범위를 정합니다. 같은 층위의 정보는 한 분류 축으로 나누고 겹침·공백·예외를 검토합니다.
- 제안은 계기와 문제 → 선택지·판단 → 실행 방법 → 평가 시점과 지표 순으로 읽히게 씁니다.
- 내부 점검에는 Why–What–How와 SWOT을 사용합니다. 읽기 흐름은 Trigger→Idea→Manual→Evaluation(time)로 확인합니다. 관측과 가정을 구분합니다.
- 회고·사례는 상황, 맡은 과제, 실제 행동, 관찰 결과와 증거를 연결합니다. 내부 점검에는 STAR를 사용합니다.
- 학습·구직 자료는 기대 태도, 수행 역량, 필요한 지식, 확인 방법을 설명합니다. 내부 점검에는 ASK(Attitude, Skill, Knowledge)를 사용합니다.
- 업무 계획·실행 자료에는 FIT(Focus, Instant, Truck)를 내부 작업 분류 기준으로 사용합니다. 핵심 목표에 집중할 일, 지금 처리할 작은 부수 작업, 나중에 처리해도 되는 기록·보류 항목을 구분하되 독자에게 분류 약어를 강제로 노출하지 않습니다.
- FIT은 작업의 성격을 나누고, ASK는 역량을, TIME은 제안의 진행·평가 시점을 설명하므로 서로 대체하지 않습니다. 기존 Tuck의 후순위 보관 의미를 Truck으로 명명 변경한 것으로 보며, 긴급도·상태와는 구분합니다. 경계가 애매하면 분류 이유와 재검토 시점을 남깁니다.
- 참고: `usagi-ai-kr/moi`는 `focus/instant/tuck`을 이슈별 단일 축으로 적용합니다. `usagi-ai-kr/yoroi`는 `memo/plan/work/report/handle/hold`처럼 기록 유형·처리 상황을 나눕니다. 서로 다른 축을 억지로 1:1 치환하거나 usagi의 기존 `type/status` 라벨을 무단 교체하지 않습니다.
- 템플릿 이름을 목차로 기계적으로 사용하지 않고 독자에게 자연스러운 제목을 씁니다.

## 메타데이터

이 계약의 검증 대상인 제안·회고·학습·구직 문서는 frontmatter로 유형과 검증 정보를 선언합니다. README/Wiki 같은 참조 문서는 필요할 때만 사용합니다.

```yaml
---
doc_type: proposal
audience: 의사결정자
evaluation: 2026-Q4 파일럿에서 완료 시간과 재작업률을 측정
---
```

- `doc_type`: `proposal`, `retrospective`, `learning`, `job-search`, `reference` 중 하나입니다.
- `audience`: 문서를 읽는 대상입니다.
- `evaluation`: proposal에 필요합니다.
- `evidence`: retrospective에 필요합니다.
- `competency`: learning/job-search에 필요합니다.
- 검사기는 키의 존재와 허용 값만 확인합니다. 내용의 질은 리뷰어가 판단합니다.

## 읽기 부담

- 문장 64자, 문단 256자, 문서 1,024자를 기본 상한으로 둡니다.
- 공백·문장부호를 포함한 유니코드 코드 포인트를 세며 Markdown 표식, 링크 주소, 코드는 제외합니다. 문단과 목록 항목은 블록 단위로 구분하고 제목은 문서 길이에 포함합니다.
- 초과는 개선 신호입니다. 중복, 범위 혼합, 과도한 배경, 계층 분리를 검토하고 의미를 훼손하는 강제 절단은 하지 않습니다.
- 상세한 증거·표·명령은 부록으로 분리합니다. 예외는 이유를 리뷰에 기록합니다.
- 이 문서처럼 참조용 문서(`doc_type: reference`)는 문서 전체 1,024자 예산에서 제외하고 문장·문단 예산만 적용합니다.

## GitHub Markdown

- 한국어 조사와 강조 경계가 모호하면 `<strong>핵심</strong>은`처럼 HTML strong을 사용합니다.
- 식별자·명령은 `토큰`은 inline code로 표기합니다. strong과 code는 의미가 다릅니다.
- 리터럴 물결표는 `\~`로 이스케이프합니다. 범위는 문맥에 따라 `-`로 씁니다. `~~텍스트~~`는 취소선입니다.
- 일반 Markdown과 GitHub Issue 모두 `- [ ]`가 렌더링될 수 있지만 상호작용은 같지 않습니다. 설명 문서에는 상태를 글로 쓰거나 번호 목록을 사용합니다.
- 게시 전 GitHub rendered view에서 조사, escape, 중첩 목록, 표, 체크 상태를 확인합니다.

## 검사

`node scripts/check-human-doc.mjs [--require-metadata] [--json] <문서.md>`

- 종료 코드 0은 길이 경고만 있는 상태, 1은 메타데이터 오류, 2는 사용법/읽기 오류입니다.
- `--require-metadata`는 모든 입력에 유효한 메타데이터를 요구합니다.
- `--json`은 기계 판독용 결과를 출력합니다.
- 길이 경고는 구조적 결함의 단서일 뿐, 품질을 자동 인증하지 않습니다.
