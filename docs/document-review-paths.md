# 문서 검토 경로 (PRD/SRS/ADR)

Source: [Issue #46](https://github.com/usagi-ai-kr/usagi/issues/46).
관련: #22, #23, #26, #14.

## 1. 목적

PRD는 "무엇을 왜", SRS는 "무엇을 검증 가능하게", ADR은 "왜 이 방식"을 남긴다. 문서 깊이는 프로젝트 규모와 위험도로 정한다. 코드 줄 수로 정하지 않는다.

## 2. 문서별 책임

| 문서 | 답하는 질문 | 필수 내용 |
| --- | --- | --- |
| PRD | 누구의 어떤 문제를 왜 푸는가 | 사용자·문제, 목표/비목표, 우선순위, 가치·성공 지표, 제품 수용 기준 |
| SRS | 시스템이 무엇을 해야 하나 | 기능·비기능 요구사항, 인터페이스·외부 계약, 제약, 오류·경계 사례, 요구사항 ID |
| ADR | 왜 이 구조·방식인가 | 배경, 결정, 대안, 트레이드오프, 영향, 검증·재검토 조건 |

세 문서는 서로를 대체하지 않는다.

## 3. 경량/전체 경로

**경량(소규모·빠름)**: ADR 중심. 이슈나 ADR에 목표, 범위, 검증 가능한 done 기준을 적는다. PRD/SRS를 강제하지 않는다.

**전체(외부 클라이언트·대규모)**: PRD → SRS → ADR → 구현/검증. 경계 조건 중 하나라도 참이면 PRD와 SRS를 모두 요구한다.

경계 기준: 팀 규모, 이해관계자, 외부 의존성, 노출 인터페이스, 변경 영향, 규제·운영 위험. 시스템 API 소비자를 외부 클라이언트로 볼지는 시작 때 정하고 기록한다.

## 4. 승격/변경 관리

- ADR로 시작한다. 외부 소비자 등장, 범위 확장, 상충하는 스펙이 생기면 PRD/SRS로 승격한다.
- 기존 ADR은 지우지 않고 승격 문서에서 링크한다.
- 요구사항 변경은 PRD/SRS와 영향받는 ADR·테스트를 함께 갱신한다.

## 5. 검토와 승인

문서 승인, 구현 승인, 배포 승인, 테스트 통과는 별개다. 모르는 것은 모른 채 남기고 추측으로 채우지 않는다.

## 6. 추적성

- 전체: PRD 목표 → SRS 요구사항 ID → 테스트 증거 → ADR. 한 줄이 끊기면 수용하지 않는다.
- 경량: 이슈/ADR 수용 기준 → 테스트 증거.

## 7. 한계/위험

- 모든 작업을 형식 문서로 만들면 경량 경로가 죽는다. 기본은 경량이다.
- "빠른 출시"를 이유로 외부 계약을 건너뛰지 않는다.
- 규모·외부 클라이언트 정의가 애매하면 판단과 이유를 기록한다.

## 8. 검토 절차

검토자는 [document-review 스킬](../.agents/skills/document-review/SKILL.md)을 따르고, 템플릿은 [document-templates.md](document-templates.md)를 쓴다.
