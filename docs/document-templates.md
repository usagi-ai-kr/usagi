# 문서 템플릿 (PRD/SRS/ADR)

Source: [Issue #46](https://github.com/usagi-ai-kr/usagi/issues/46).
경로 판단 기준은 [document-review-paths.md](document-review-paths.md)에 있다.

템플릿은 시작점이다. 독자와 프로젝트에 맞게 줄이거나 늘린다. 경량 경로에서는 모든 필드를 요구하지 않는다. 선택 필드는 `(선택)`으로 표시했다. 나머지는 전체 경로에서 채운다.

## PRD 템플릿

```markdown
# <제품/기능 이름>

## 문제와 사용자
<누가, 무엇 때문에, 어떻게 불편한가. 지금 어떻게 해결하는가>

## 목표 / 비목표
- 목표: <이번에 달성하는 것>
- 비목표: <이번에 하지 않기로 한 것>

## 우선순위
<순위 또는 must/should/could>

## 성공 지표
<측정 가능한 가치 지표. 측정 방법 포함>

## 제품 수용 기준
<사용자 관점에서 완료를 판정하는 조건>

## 열린 질문 (선택)
<모르는 것. 추측으로 채우지 않고 소유자에게 묻는다>
```

## SRS 템플릿

```markdown
# <시스템/구성요소 이름>

## 범위
<이 문서가 다루는 시스템 경계와 다루지 않는 것>

## 기능 요구사항
- REQ-F-001: <검증 가능한 한 문장>
- REQ-F-002: ...

## 비기능 요구사항 (선택)
- REQ-N-001: <성능·신뢰성·보안 등 제약>

## 인터페이스/계약
<외부 시스템·API·파일 형식과의 약속. 소비자가 누구인지 포함>

## 오류/경계 사례
<입력 경계, 실패 시 기대 동작>

## 테스트 매핑
| 요구사항 | 테스트/증거 |
| --- | --- |
| REQ-F-001 | <테스트 이름 또는 수용 증거> |

## 열린 질문 (선택)
```

## ADR 템플릿

```markdown
# ADR-<번호>: <결정 제목>

## 배경
<어떤 상황에서 어떤 요구·제약이 작용했는가>

## 결정
<한 문장 결정과 필요한 보충>

## 대안과 트레이드오프
<고려한 대안과 기각한 이유>

## 영향
<무엇이 쉬워지고 무엇이 어려워지는가>

## 검증
<결정이 잘 적용됐는지 확인하는 방법>

## 재검토 조건 (선택)
<이 조건이 참이면 다시 논의한다>

## 링크 (선택)
<관련 PRD/SRS/이슈/이전 ADR>
```
